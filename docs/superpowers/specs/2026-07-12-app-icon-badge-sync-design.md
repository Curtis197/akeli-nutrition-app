# App Icon Badge Sync — Design

## Goal

Push notifications now deliver correctly (fixed in this session — the
Firebase project was missing a production APNs key). But the OS app-icon
badge doesn't behave correctly on top of that: it's hardcoded to `1` by the
server on every push and nothing in the app ever clears or updates it, so it
never reflects real unread count and never goes away when a user reads their
notifications in-app.

## Current State

- `fcm.ts`'s `sendFcmV1` hardcodes `apns.payload.aps.badge = 1` on every send
  ([supabase/functions/_shared/fcm.ts:112](../../../supabase/functions/_shared/fcm.ts)).
- `unreadNotificationCountProvider` ([lib/providers/notifications_provider.dart](../../../lib/providers/notifications_provider.dart))
  already tracks the true unread count from the `notification` table and is
  used for the in-app bell badge.
- `markAllNotificationsRead()` already flips `is_read = true` in the DB and
  invalidates `unreadNotificationCountProvider` when the Notifications page
  opens.
- Nothing in the codebase calls any native badge API (`grep` for
  `applicationIconBadgeNumber` / `flutter_app_badge` / `AppBadge` returns
  nothing) — the OS badge is entirely unmanaged on the client.

## Approach

Two independent, composable fixes:

### 1. Server: send the real unread count

In `send-push-notification/index.ts`, right after the existing STEP 4 insert
into `notification`, add one query for the current unread count
(`is_read = false`) for that `user_id`, and pass it through to `sendFcmV1` as
the `badge` value instead of the hardcoded `1`. This makes every push carry
an accurate badge number, covering the case where the app is closed and never
reopened before the next push arrives.

### 2. Client: sync badge to the same provider that drives the in-app bell

Add `flutter_app_badge_control` (pub.dev, MIT, mature — iOS supports exact
counts via `updateBadgeCount()`; Android only supports `removeBadge()` since
there's no universal cross-launcher API for exact counts — this is a platform
limitation, not a package gap).

New `lib/providers/badge_sync_provider.dart`:

```dart
final badgeSyncProvider = Provider.autoDispose<void>((ref) {
  _logger.provider('badgeSyncProvider build()');
  ref.onDispose(() => _logger.provider('badgeSyncProvider disposed'));

  ref.listen<AsyncValue<int>>(unreadNotificationCountProvider, (_, next) {
    next.whenData((count) async {
      try {
        if (count == 0) {
          await FlutterAppBadgeControl.removeBadge();
        } else {
          await FlutterAppBadgeControl.updateBadgeCount(count);
        }
        _logger.provider('badgeSyncProvider → synced | count: $count');
      } catch (e, st) {
        _logger.provider('badgeSyncProvider → ERROR | $e', error: e, stackTrace: st);
      }
    });
  }, fireImmediately: true);
});
```

Wired into `main_shell.dart` next to the existing
`ref.watch(pushTokenProvider);` line with `ref.watch(badgeSyncProvider);` —
same lifecycle pattern already established for FCM setup.

## Data Flow

1. Push arrives (app closed or backgrounded) → server-set `badge` count in
   the payload updates the OS badge directly (no app code runs).
2. User opens the app → Notifications page → `markAllNotificationsRead()` →
   `unreadNotificationCountProvider` invalidates → resolves to `0` →
   `badgeSyncProvider`'s listener fires → `removeBadge()` → OS badge clears
   immediately. This is the path that was silently missing before and is the
   direct fix for the reported bug.
3. New notification arrives while app is foregrounded → existing SnackBar
   flow shows it, `notificationsProvider`/`unreadNotificationCountProvider`
   aren't automatically invalidated by the foreground FCM listener today —
   out of scope for this fix (badge staying stale while the app sits
   foregrounded and a push silently lands is a separate, pre-existing gap in
   `main.dart`'s `onMessage` handler, not part of this task).

## Error Handling

All plugin calls wrapped in try/catch with `_logger.provider(...)` on
failure, per the logging standard. A badge-sync failure must never crash the
app or block any other flow — worst case the badge is stale, which is the
status quo today.

## Scope

- `pubspec.yaml` — add `flutter_app_badge_control` dependency
- `ios/Podfile.lock` — regenerated by `pod install`
- `lib/providers/badge_sync_provider.dart` — new
- `lib/shared/widgets/main_shell.dart` — one line added
- `supabase/functions/send-push-notification/index.ts` — unread-count query
  + pass `badge` through
- `supabase/functions/_shared/fcm.ts` — `sendFcmV1` takes a `badge: number`
  param instead of hardcoding `1`

## Out of Scope

- Making Android badge counts exact (platform limitation — remove-only is
  the ceiling for this package; a fuller solution would mean per-OEM native
  code, not justified by current scope).
- Live-updating the badge while the app sits foregrounded and a push lands
  without the user navigating to Notifications (pre-existing gap in the
  foreground FCM handler, unrelated to the reported bug).
